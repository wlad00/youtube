# Почему все говорят про Ponytail?

## Кратко

Автор канала Swag проверяет плагин-скилл Ponytail: набор правил в одном Markdown-файле, который задаёт агенту режим «ленивого сеньора» — минимальные изменения и короткие ответы. Сначала он критикует репозиторий: вокруг одного файла на 52 строки огромная обвязка, а цифры из README (меньше кода, быстрее, дешевле) выглядят как маркетинг. Затем он сравнивает две сессии в Open Code на модели DeepSeek: создание CLI, который считает топ-10 фильмов по рейтингу IMDb, с правилами Ponytail и без них. С правилами получилось 109 строк кода против 647, токенов потрачено меньше, а рейтинг оказался корректнее: решение отфильтровало фильмы с малым числом голосов. Но у этого варианта есть минусы: зависимость, паника из-за unwrap, а версия без правил выиграла по нулевым зависимостям и тестам. Вывод автора: короткие правила стоит копировать, даже если модель умная, потому что модель в проекте может смениться. Спорно: это один эксперимент на одной задаче и одной модели без повторов; оценка «корректнее» основана на субъективном сравнении результатов; а цифры репозитория автор сам считает подозрительными.

## Разделы

### 1. Две школы промтинга и тезис «выбросьте скиллы» — 00:00:02–00:01:03
Автор говорит, что в промтинге есть две школы: одни доверяют агенту самому решать, как писать код, другие добавляют много скиллов, чтобы направлять модель. Он ссылается на прошлый выпуск, где обсуждали, что LLM остаются инструментом и их нужно направлять. Каждый выход новой модели, по его словам, заставляет пересматривать скиллы, потому что их нужно всё меньше, и программисты снова и снова советуют выбросить все скиллы. Проверять это он будет на DeepSeek, а не на Opus.

### 2. Репозиторий: один файл среди обвязки — 00:01:03–00:03:07
Автор открывает репозиторий Ponytail и сообщает, что нужный файл найти было непросто: под каждую систему есть свой плагин, а вокруг много бенчмарков, скриптов, примеров и тестов. Сам скилл, по его словам, лежит в папке skills и занимает около 52 строк. Остальное — установка и обвязка. Поэтому, говорит автор, правила можно просто скопировать в свой agent.md. Он признаётся, что сам устанавливает скиллы копированием, потому что после обновлений всё ломается.

### 3. Цифры в README и скепсис автора — 00:03:07–00:04:39
В README указана версия 5 и цифры: меньше 51–53% кода, работа быстрее примерно на 40%, стоимость на 26% ниже и на 45% меньше токенов. Автор иронизирует над стилем README, похожим на рекламу AI-стартапа. Он отмечает, что у Markdown-файла есть спонсоры и 160 тысяч звёзд на GitHub, и считает это странным для простого текстового файла. Поэтому, говорит он, сначала надо понять, что скилл делает на самом деле.

### 4. Что делает Ponytail: режим «ленивого сеньора» — 00:04:39–00:07:46
По описанию, Ponytail включает режим ленивого сеньор-разработчика: минимальные изменения, полностью решающие задачу, и короткие ответы, которые понятны с первого прочтения. Есть уровни light, full, default и ultra. Правила короткие: лучший код — тот, который не написан; перед работой агент читает задачу и затронутый код, перечисляет все места правок, проверяет, что изменение может сломать для пользователей. Ещё правила: искать похожие решения в кодовой базе, использовать стандартную библиотеку и не добавлять зависимость ради нескольких строк.

### 5. Эксперимент: CLI для топ-10 фильмов IMDb — 00:07:46–00:09:51
Автор повторяет задачу из прошлого выпуска, где сравнивали языки: создать CLI, который строит топ-10 фильмов по рейтингу IMDb. Он создаёт проект с правилами Ponytail в Agents.md и копию без них. Обе сессии запускаются в Open Code на модели DeepSeek с высоким уровнем рассуждений. По токенам первая сессия потратила около 49 тысяч, вторая — около 36 тысяч. Автор просит сравнить сессии и реализации, включая метрики кода.

### 6. Сравнение результатов: строки, рейтинг и стоимость — 00:09:51–00:13:30
Версия без правил содержит 647 строк кода, версия с Ponytail — 109. Результаты тоже различаются: в версии с правилами первой стоит другой фильм, а в версии без правил конфиг с множеством параметров, который автор не просил. Версия с правилами, по его наблюдению, сама решила фильтровать фильмы с малым числом голосов, то есть корректнее посчитала IMDb-рейтинг. По AI-анализу, Ponytail тратит меньше токенов на вход и заметно меньше на выход, итоговая стоимость примерно в полтора раза ниже.

### 7. Детали реализации и минусы — 00:13:30–00:16:09
У версии с Ponytail 180 строк, у базовой — 600. Тестового кода в первой 70 строк, во второй — 468. Версия с правилами выбрала другой Language Edition у Rust и взяла одну зависимость для CSV, которую базовая версия написала вручную. Простая версия потратила на работу 5 минут, версия с Ponytail — 3 минуты. По итогам базовая версия выиграла по нулевым зависимостям и восьми тестам, а в версии с правилами нашлась паника из-за unwrap.

### 8. Выводы автора и оговорки — 00:16:09–00:17:44
Автор говорит, что Ponytail действительно работает, и что короткие правила он сам скопировал бы себе, потому что модели в проекте могут переключаться и на слабую модель полагаться нельзя. Он советует посмотреть бенчмарки самого автора Ponytail, отмечает, что сравнивал его с другим скиллом Caveman, и предлагает записать о нём отдельный выпуск, если зрителям интересно. Выпуск заканчивается призывом поставить лайк и подписаться.
