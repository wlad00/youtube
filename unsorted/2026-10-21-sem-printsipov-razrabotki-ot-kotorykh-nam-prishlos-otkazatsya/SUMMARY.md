# Семь принципов разработки, от которых нам пришлось отказаться

## Кратко

Автор считает, что привычные принципы разработки перестали работать из-за объёма кода, который пишут ИИ-агенты: по его словам, число коммитов на GitHub за год выросло в пятнадцать раз при том же числе программистов (00:00:34). Он называет семь принципов, которые пересмотрел: от читаемости кода до стабильности главной ветки. Каждый подкрепляет опытом: старый Java-проект, который агент починил за неделю, правило на двести строк в pull request, сборка main, которая почти всегда сломана. Итог: ревьюер и человеческое внимание стали помехой, код читают агенты, скорость важнее стабильности. Спорно: доказательств мало, опора на личный опыт и на исследование без источника, а прогноз про отмену diff автор сам назвал шуткой (00:17:18).

## Разделы

### 1. Читаемость кода и комментарии — 00:01:40–00:03:15
Автор начинает с давнего убеждения: код должен быть понятен читателю, поэтому сложные алгоритмы сопровождают комментариями. Теперь, по его словам, код читают только агенты, а комментарии их путают. Он ссылается на исследование о вреде комментариев, но источника не называет. Поворот в 00:02:44: цель — минимальный код, поэтому в его проектах комментарии запрещены в скриптах сборки, в Haskell и JavaScript полностью, а в Java к этому идут.

### 2. Старый код: оживлять, а не переписывать — 00:03:15–00:05:22
Раньше старый код, который не собирается и тянет устаревшие зависимости, выбрасывали и писали заново, теперь автор предлагает его оживлять. Пример: статический анализатор на Java, созданный лет десять назад, с более чем четырьмястами накопившихся задач. Весной он поручил ИИ-агенту закрыть их и обновить проект, и за неделю без ручных правок получился рабочий проект. Автор упоминает статью, где похожее восстановление заняло три недели вместо полутора лет. Вывод: термина «legacy» больше нет.

### 3. Ручной разбор багов и pull request — 00:05:22–00:09:32
Раньше главная задача архитектора, по словам автора, — отделять настоящие баги и смотреть pull request. Теперь человеческое внимание он считает вредным: объём растёт, код пишут роботы, ручной разбор только тормозит проект. Его проект с полутора тысячами звёзд получает около ста баг-репортов в день, и агент каждое утро сам принимает баги, а к вечеру вливает сорок–пятьдесят pull request. Оговорка (00:08:29): сложные изменения агент оставляет автору на проверку, таких несколько в день. Вывод: ревьюеры больше не нужны (00:09:00).

### 4. Вежливость к авторам pull request — 00:09:32–00:11:38
Автор признаёт, что раньше учил студентов уважать контрибьюторов: благодарить, извиняться, ведь программисты вернутся с новым кодом. Теперь он считает, что за pull request стоит не программист, а тот, кто запустил агента, нажал кнопку и ушёл, поэтому переговоры бессмысленны. Ценность людей, которые анализируют изменения, по его словам, ниже, чем у машин. Вывод: быть максимально строгим и закрывать предложения без обсуждения, ведь на другой стороне никто не обидится.

### 5. Автоматические ограничения размера — 00:11:38–00:13:41
Раньше команды спорили о размере pull request: сто–двести строк считались нормой, тысяча — явным признаком плохой работы. Примерно полгода назад автор добавил в GitHub скрипт, который делает проверку красной, если в pull request больше двухсот строк, и оспорить её нельзя. Такие флаги, по его мнению, нужны во всех репозиториях: агент увидит красный статус, разобьёт изменение на части, и никто не обидится. Цель — нулевая терпимость к низкому качеству, которое закрывается автоматическими проверками (00:13:10).

### 6. Читать не код, а результаты и влияние — 00:13:41–00:18:49
Автор говорит, что его двухтомник по unit-тестам теперь нужен только машинам. Вместо чтения кода он описывает текстовые файлы-фикстуры: в парсере один тест и много файлов, где рядом видны входной код и ожидаемый XML (00:14:43). По такому файлу человек принимает или отклоняет pull request, даже не понимая код агентов. Он ссылается на Роберта Мартина, который тоже перестал читать исходный код, и советует измерять влияние каждого pull request (00:18:19).

### 7. Стабильность главной ветки против скорости — 00:19:21–00:24:02
Автор вспоминает, что непрерывная интеграция задумывалась как ежедневная сборка, а позже появилась предварительная сборка перед попаданием в main. При ста pull request в день и сборке около десяти минут очередь не справляется: каждое изменение main делает остальные проверки устаревшими. Поэтому, по его словам, главная ветка почти постоянно сломана, и агенты должны сами заметить поломку и починить её (00:22:59). Вывод: стабильность осталась в прошлом, современная идея — скорость (00:24:02).
